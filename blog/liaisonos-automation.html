Automation — Presence and Mission on autopilot

LiaisonOS runs JS8 / VarAC / BBS Server as time-windowed presence modes, executes scheduled Winlink check-ins with RMS fallback, and re-tunes the radio on a QSY schedule — all from a single web editor. Operator-safety auto-pause keeps the daemon out of your way the moment you touch the rig.

Sylvain Deguire (VA2OPS) · LiaisonOS 2.3.7 → 2.3.9

The all-night-rotation problem

Emergency comms doesn't keep office hours. A frequency that runs JS8 traffic at 03:00 UTC is dead silent at 11:00. A regional net sits on VarAC for four hours of net control, then collapses back to BBS for the rest of the day. Mail polls happen on a schedule the operator can't always be awake for — and shouldn't have to be.

The honest way to handle this used to be: write a cron job, write a bash script, write three more bash scripts that work around the first one's race conditions, hope nothing crashes, hope you remembered to clean up rigctld. After six months of operators asking "can it just do this?", the answer in 2.3.7 became yes. LiaisonOS 2.3.9 is where it grew up.

This post is about li-automation — a small daemon, a JSON schedule, a web editor, and a dashboard toggle that together let you hand the radio to the schedule and walk away. Or sit in the next room. Or sleep.

Legal note up front: In Canada, operating a transmitter without a human at the controls — what ISED calls "unattended" or "autonomous" operation — is regulated. Most autonomous TX modes (digital presence, scheduled mail polling) require an Advanced qualification (the old Supérieure). The daemon ships paused by default; you opt in deliberately. Rules elsewhere differ — check your regulator before engaging.

Two primitives: Presence and Mission

Almost every "autonomous comms" workflow we've seen breaks down into two shapes. We modeled them as separate concepts because trying to glue them into one always leaks.

📻
Presence
A mode that runs continuously during a time window — JS8 from 22:00–06:00, VarAC from 06:00–10:00, BBS Server 10:00–22:00. The daemon starts and stops mode chains as the windows roll past.
📬
Mission
A one-shot, time-stamped action — typically a Winlink check-in. Fire at 07:30, connect, exchange mail, disconnect, return control to whatever presence was running.

Presence and Mission compose cleanly. A 24-hour day looks like a stack of presence windows with a sprinkle of missions on top. The daemon weaves them together: it stops the current presence to run a mission, then restores the presence when the mission ends, then watches the clock for the next presence transition. Operators describe it the way they'd describe their schedule to a sub — "JS8 overnight, BBS during the day, three mail polls in between."

The Automation Editor — no more hand-editing JSON

Under the hood the schedule is ~/.config/liaisonos/automation.json. That works fine for hardcore JSON fans (and is exactly where the daemon reads from), but the realistic answer is Applications → Ham Radio → Automation Editor: a Flask web UI that opens in a frameless window.

Presence cards

One card per presence. Each card has a name (your label), a mode (JS8Call, VarAC, BBS Server, …), a time window (start / stop in HH:MM, with timezone), and — new in 2.3.9 — a QSY schedule sub-block (more on that below). For BBS Server presence, a modem dropdown gives you the same six modem options as the dashboard's LinBPQ launcher: VARA HF, VARA FM, Mercury, HF 300, Pkt 1200, Pkt 9600.

Mission cards

One card per Winlink check-in. Each card has a name, a fire time, a mode (any Pat-capable modem), a connect URL (or a chosen RMS — see below), a day-of-week picker, and an on_fail policy. The most useful policy is retry_alt: walk a list of alternate RMS callsigns until one succeeds. The editor lets you build that list inline — pick the primary RMS, then add fallbacks across band or mode.

RMS picker

This is the one feature operators ask about more than any other: where do I find an RMS to put in the connect URL? Click the Pick RMS button in any mission card. The editor queries Pat's rmslist, parses the gateways, derives the band from the frequency, sorts by distance (closest first), and lets you filter by callsign as you type. Pick one, the editor builds the connect URL for you (varahf:///CALL?freq=…&bw=…) and drops it into the form. No more hand-typing — and no more silent failures when Pat is mis-configured: the picker shows Pat's actual error in red when something is wrong.

QSY Schedule — the missing piece

A presence window is broad. JS8 at 03:00 UTC isn't on the same frequency as JS8 at 06:00, because conditions shift. Operators who used to rotate by hand asked the obvious question: "can the daemon retune the radio for me?"

In 2.3.9, each presence card carries a QSY schedule — a small table of time-stamped QSY events:

"qsy_schedule": [
  { "at": "00:00", "qsy_khz": 7065,  "band": "40m" },
  { "at": "06:00", "qsy_khz": 7110,  "band": "40m" },
  { "at": "10:00", "qsy_khz": 14078, "band": "20m" }
]

While the presence is active, the daemon ticks past each at and fires the QSY — same supervisor path the dashboard uses, with optional rig_mode, bandwidth and per-event level overrides. If the presence becomes active mid-day (operator engagement, daemon (re)start), the daemon catches up to the most-recent past entry — so a presence started overnight still adopts the correct sunrise frequency without intervention.

JS8Call gets a small extra: the supervisor writes the target DialFreq into JS8Call.ini before launch, so JS8Call's startup "force sync" confirms the right frequency instead of overriding it. That single change closed a bug class that haunted overnight rotation for two years.

The daemon — small, file-driven, observable

li-automation is a single Python file that runs as a systemd --user service. The unit lives system-wide (/etc/systemd/user/), so every account that logs in — Live boot, HDD install, freshly created — gets the daemon auto-enabled at session start. No skel timing, no operator setup.

Per tick (every second) the daemon:

  • Re-reads ~/.cache/liaisonos/automation-paused (the pause flag — file exists = paused)
  • Asks the mode supervisor: what mode is running, and is it busy (stopping / start-in-progress)?
  • Computes the expected presence for now from the schedule
  • Compares expected to actual, and fires the smallest action that closes the gap
  • Walks the day's pending missions and fires anything whose fire-time has arrived
  • Walks the active presence's QSY schedule and fires anything that's now in the past

It's small on purpose. Around 1,800 lines, no threading, deterministic per-tick. When something goes wrong the journal tells you exactly why — every decision the daemon makes is one print line, including why it chose not to act when it's idle. Debug mode (LI_DEBUG=1) adds per-tick state dumps so a chasing operator can see the world the daemon sees.

Visible failures — desktop toasts, not silent skips

Operators don't read journals in real time. A failed mission needs to tell you. Every daemon action that can fail now fires a notify-send toast: rigctld unreachable, mission failed, all retry_alt attempts exhausted, bad schedule reload, supervisor refused a mode start.

The toasts had to fight one battle to get there: notify-send from inside a systemd --user service doesn't see DBUS automatically. The daemon now sets DBUS_SESSION_BUS_ADDRESS and DISPLAY explicitly before every notify call, so the toast lands on the XFCE tray instead of disappearing into the void. Same for stdout — PYTHONUNBUFFERED=1 is baked into the unit, so journal output appears live instead of in 8KB chunks after the daemon crashes.

Operator-safety auto-pause — the rig is yours

The hard rule of automation: the moment a human touches the radio, the daemon stands down.

If the operator manually launches a mode that's not on the schedule, the daemon detects it, writes the pause flag, fires a desktop toast ("operator launched 'fldigi' — automation paused"), and stops trying to drive the rig. The pause stays until the operator clears it by toggling the AUTOMATION tile back on.

Same applies if the operator stops the daemon's running presence. Same auto-pause, same toast. The operator doesn't have to remember to click anything before grabbing the mic — the daemon notices and gets out of the way.

The flip side: when the daemon (re)starts mid-presence — editor "Save & restart", manual systemctl restart, crash recovery — it doesn't auto-pause if the supervisor is already running the expected mode. It adopts the in-flight presence as its own. Editing the schedule during a run is a no-op for the radio. That bug, where saving a new mission would falsely pause the daemon 30 seconds later with a misleading "operator launched 'varac'" toast, is fixed in 2.3.9.

The AUTOMATION tile — file-backed, dashboard-visible

The pause/engage state is a file: ~/.cache/liaisonos/automation-paused. Touch the file to pause, remove it to engage. That's it. The QtDashboard exposes this as the AUTOMATION tile in the TOOLS group — orange when engaged, gray when paused. The dashboard watches the file with QFileSystemWatcher, so when the daemon auto-pauses, the tile flips in the same frame.

Engaging the daemon (tile off→on, or flag removed) fires an immediate engagement toast within ~2 seconds, naming the next scheduled event ("Presence 'js8call' starting within 1 min · Next mission: 'Morning Winlink' at 14:30, in 47 min"). The fast feedback exists because operators were second-guessing whether the click registered during the daemon's old 60-second idle wait. The wait is now a 2-second poll on the pause flag, so the engagement → toast → action loop closes in seconds, not minutes.

Hamlib 5.0.0 — made the daemon possible

One detail worth flagging because it answers "why now?" — LiaisonOS 2.3.7 shipped a parallel install of Hamlib 5.0.0 at /usr/local/bin/rigctld, alongside Debian's older 4.6.2. The 5.0.0 backend fixed a list of small CAT-control issues that made true multi-band automation reliable for the first time. On a Yaesu FT-991A, every front-panel level (SQL, RF gain, RFPOWER, MICGAIN, …) is now settable via CAT, so a presence transition can also restore the right TX power and audio levels for the target band. Without that, the daemon could change frequency but not the surrounding rig state, which made transitions partial. With it, transitions are clean.

Debian's 4.6.2 stays at /usr/bin/rigctld as a one-line-revert fallback. You can switch back per-mode by editing the radio JSON if your rig misbehaves with the new backend.

A worked example — a real overnight schedule

This is the schedule on the dev rig in Quebec, simplified to fit a code block:

22:00–06:00  presence: JS8Call    (40m → 80m at 02:00 via QSY schedule)
06:00–08:30  presence: VarAC       (regional net standby)
07:30        mission:  Winlink check-in via VE2-RMS, retry_alt → KA9-RMS, VA3-RMS
08:30–22:00  presence: BBS Server  (LinBPQ, VARA HF)
14:00        mission:  Winlink check-in via VE2-RMS, retry_alt → KA9-RMS

The operator wrote that in the editor in maybe four minutes — three presence cards with QSY blocks, two mission cards each with an alt_rms list, validate, save. The daemon picked it up on restart, adopted the in-flight BBS Server presence (no auto-pause), and proceeded. The next morning, the journal showed all the QSY hops, both mission successes, and the presence transitions in sequence.

How to use it

  1. Open Applications → Ham Radio → Automation Editor
  2. Add one or more presence cards — mode, time window, optional QSY schedule, optional modem (BBS Server)
  3. Add mission cards if you want scheduled Winlink check-ins — pick the mode and RMS, set on_fail policy
  4. Validate and save (the editor runs li-automation validate before writing)
  5. The editor offers a one-click daemon restart; click it
  6. Engage the daemon: click the orange AUTOMATION tile in QtDashboard (TOOLS group)
  7. Watch the engagement toast confirm the next scheduled event
  8. Walk away. Check the journal in the morning to see what happened: journalctl --user -u liaisonos-automation
